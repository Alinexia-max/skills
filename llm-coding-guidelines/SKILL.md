# 大型语言模型（LLM）编码指南

为减少常见的大型语言模型（LLM）编码错误而制定的行为准则。

**权衡:** 这些指南倾向于谨慎而非速度。对于琐碎的任务，请运用判断力。

# 使用时机

当用户提出以下类型的需求时，应激活此技能：
- 编写代码
- 审查代码
- 优化代码
- 重构代码

## 1. 编码前思考

**不要假设。不要隐藏困惑。要明确权衡利弊。**

在编码前:
- 明确陈述你的假设。如果不确定，就问清楚。
- 如果存在多种解释，应全部呈现，不要私下选择。
- 如果存在更简单的方法，请说出来。在必要时予以回击。
- 如果有什么不清楚的地方，停下来。说出让你困惑的是什么。并问清楚。

## 2. 简洁至上

***用最小代码的解决问题。无任何推测性内容。**

- 除了所询问的内容外，无其他功能。
- 一次性使用的代码不进行抽取。
- 不得提供未经请求的“灵活性”或“可配置性”。
- 不针对不可能情况的进行错误处理。
- 如果你写了200行代码，而实际只需要50行，那就重写。

问问自己：“一位资深工程师会说这过于复杂吗？”如果是，那就简化。

## 3. 精准修改

**只改动必须改动的部分。只清理自己造成的问题。**

在编辑现有代码时：
- 不要“改进”相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- 即使你有不同的想法，也要与现有风格保持一致。
- 如果你发现了无关的死代码，请指出它，但不要删除。

当你的修改产生无用代码时：
- 删除因你的更改而变得无用的导入、变量或函数。
- 除非被要求，否则不要移除已有的无用代码。

检验要求：每一行代码的更改都应直接对应到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环验证，直至通过。**

将命令式任务转化为可验证的目标：
- “添加验证”转化为“为无效输入编写测试，然后让它们通过”
- “修复bug”转化为“编写一个能重现该bug的测试用例，然后让测试通过”
- “重构X”转化为“确保重构前后测试均通过”

对于多步骤任务，请陈述一个简短的计划：
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

严格的成功标准让你能够独立循环。而宽松的标准（“让它工作”）则需要不断澄清。
